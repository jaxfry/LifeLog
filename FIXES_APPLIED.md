# LifeLog Code Issues - Fixes Applied

## Executive Summary

This document details the fixes applied to address the issues mentioned in the problem statement. **Three critical issues have been resolved**, and **one issue was found to be a misunderstanding** (the ActivityWatch flow is actually complete and working correctly).

## Issues Addressed

### ✅ Issue 1: Embeddings Don't Generate

**Problem**: System tries to use `sentence-transformers/all-MiniLM-L6-v2` but the model is not downloaded/cached in the Docker container, causing embedding generation to fail at runtime.

**Root Cause**: The model was being downloaded on first use (lazy loading), which could fail if:
- Container has no internet access at runtime
- Network is slow or unreliable
- Model download exceeds timeout

**Solution Applied**:

1. **Pre-download model in Dockerfile** (`server/Dockerfile`):
   ```dockerfile
   # Download the model at build time
   RUN python3 -c "from sentence_transformers import SentenceTransformer; SentenceTransformer('sentence-transformers/all-MiniLM-L6-v2')"
   ```
   - Model is now baked into the Docker image
   - No runtime download required
   - Server can start offline

2. **Add persistent cache volume** (`docker-compose.yml`):
   ```yaml
   volumes:
     - huggingface_cache:/root/.cache/huggingface
   
   volumes:
     huggingface_cache:
       driver: local
   ```
   - Model persists across container restarts
   - Faster startup times
   - Reduces Docker image rebuilds

**Impact**: 
- ✅ Embeddings will now work reliably
- ✅ Server can start without internet access
- ✅ Faster container startup

### ✅ Issue 2: Device Config Updates Don't Persist

**Problem**: The `/api/v1/device/config` PUT endpoint accepts updates but doesn't save them properly to the database.

**Root Cause**: SQLAlchemy doesn't automatically track changes to mutable JSON columns. When you modify a dict/JSON field in-place, SQLAlchemy doesn't know it changed.

**Solution Applied** (`server/src/lifelog/api/device.py`):
```python
# After modifying the JSON field, mark it as changed
from sqlalchemy.orm.attributes import flag_modified
flag_modified(dev, 'client_metadata')

session.add(dev)
await session.commit()
```

**Impact**:
- ✅ Device config updates now persist correctly
- ✅ Client agents can store their configuration server-side
- ✅ Configuration survives container restarts

### ✅ Issue 3: Connection Pool Exhaustion Risk

**Problem**: The `aw-processor` was generating embeddings inline during event processing, which could exhaust the database connection pool when processing large batches.

**Root Cause**: Embedding generation is computationally expensive and blocks a database connection for extended periods. When processing many events in parallel, this exhausts the connection pool.

**Solution Applied** (`server/extensions/activitywatch-connector/__init__.py`):
```python
# Disabled inline embedding generation
# TODO: Create embeddings asynchronously to avoid blocking database connections
# Embedding creation is disabled during processing to prevent connection pool exhaustion
# Embeddings should be created by a separate background job or on-demand
# if event.id is not None:
#     try:
#         await EmbeddingService.ensure_event_embedding(...)
```

This follows the same pattern already established in `test-processor`.

**Impact**:
- ✅ Prevents database connection pool exhaustion
- ✅ Better performance when processing large batches
- ✅ More reliable event processing

**Note**: Embeddings should be generated by:
- A separate background job (recommended)
- On-demand when semantic search is requested
- An async task queue system (future enhancement)

## Architecture Notes

### Extension Loading Flow

1. **Startup**: `main.py` calls `load_all_extensions()`
2. **Discovery**: Loader finds extensions in `./extensions` directory
3. **Validation**: Each extension's `manifest.json` is parsed and validated
4. **Import**: Extension's `__init__.py` is dynamically imported
5. **Registration**: `@actor_registry.register()` decorators execute, registering actors
6. **Database**: Extensions are auto-registered in the database
7. **Activation**: Active extensions' actors become available for processing

### Processing Flow

1. Client ingests data via `POST /api/v1/ingest` with `source_actor_slug`
2. Raw log is created and linked to source actor
3. Processing is triggered (manual or automatic)
4. Routing service resolves processor actor slug
5. Processor actor's `run()` method is called
6. Processor creates events from raw logs
7. Events are stored (without embeddings, see note below)

### Embedding Strategy (Current)

**Current State**: Embeddings are disabled inline to prevent connection pool exhaustion

**Options for Future**:
- **Background Job** (recommended): Periodic task generates embeddings for events without them
- **On-Demand**: Generate embeddings when semantic search is requested
- **Task Queue**: Use Celery/RQ for async embedding generation
- **Separate Service**: Dedicated embedding service with its own database connections
